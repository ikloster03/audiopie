## Context

Today `electron/main/project.ts` holds a single global `ProjectData` (`{ tracks, chapters, metadata }`) in memory, backed by one `.audiopie` file that is plain JSON. `tracks[].path` is always an absolute filesystem path to a source MP3 that lives *outside* the project file — the project file is really just a manifest of pointers, not a self-contained document. The in-progress `project-types-and-series` change (33/37 tasks marked done in `tasks.md`, but the actual code for it was reverted — see git history: only the OpenSpec docs commit for it survived) doubled down on this pointer model: a `series` project would have been *yet another* `.audiopie` file whose only content is a list of paths to other `.audiopie` files.

This change replaces the pointer model with a container model: one `.audiopie` file (a ZIP) that owns its audio data, for both a single audiobook and a multi-book series. `electron/main/ffmpeg.ts`'s build pipeline is unaffected in spirit — it already needs real files on disk, it just reads them from an extracted working directory instead of wherever the user's original MP3s happened to sit.

**RU:** Сейчас `electron/main/project.ts` хранит единый `ProjectData` в памяти, файл `.audiopie` — обычный JSON, а `tracks[].path` — абсолютный путь к MP3 вне файла проекта. Незавершённый change `project-types-and-series` продолжал эту модель указателей (серия как файл со списком путей к другим файлам). Этот change заменяет модель указателей моделью контейнера: один `.audiopie`-файл (ZIP), владеющий своими аудиоданными и для одной книги, и для серии.

## Goals / Non-Goals

**Goals:**
- Make `.audiopie` a self-contained, portable container that owns its audio (survives moving/renaming source MP3s, survives being copied to another machine).
- Represent both `audiobook` and `series` projects with one file format and one *identical on-disk book-folder shape*, differing only in how many book folders the root manifest lists — so switching between the two types later is a metadata-only operation, never a file-restructuring one.
- Keep the existing "1 track = 1 chapter, sequential start/end" behavior and the FFmpeg build pipeline conceptually unchanged — they just read from an extracted working directory now.
- Preserve backward-compatible *opening* of every existing plain-JSON `.audiopie` file; upgrade to the new format happens transparently on save, not as a separate required migration step.
- Let a project's type be changed after creation (not just chosen once up front), since the structural unification above makes this safe and cheap.

**RU (цели):** Сделать `.audiopie` самодостаточным переносимым контейнером, владеющим своим аудио. Представить `audiobook` и `series` одним форматом файла с идентичной структурой папки книги на диске — переключение типа впоследствии — это только изменение метаданных, никогда не реструктуризация файлов. Сохранить поведение «1 трек = 1 глава» и пайплайн сборки FFmpeg. Сохранить обратно совместимое открытие всех существующих JSON-файлов; обновление формата — прозрачно, при сохранении. Дать возможность менять тип проекта и после создания.

**Non-Goals:**
- Backward compatibility for *opening* a new-format ZIP `.audiopie` in an older AudioPie version — this is a one-way upgrade at the file level (see Migration Plan).
- Cloud sync / real-time collaborative editing of a container while it's open in two places at once.
- Renaming chapter files on disk to always match display order after a drag-and-drop reorder (see Decisions — filenames are stable storage keys, not a display-order mirror).
- A general-purpose "repair/relink missing file" tool for a container whose internal `index.json` references a book folder that's gone (index.json fully owns book folders now, so this scenario shouldn't occur in normal use; out of scope to defend against manual ZIP tampering).

**RU (не цели):** Обратная совместимость открытия нового ZIP-формата в старой версии приложения. Совместное редактирование одного контейнера из двух мест одновременно. Переименование файлов глав на диске под порядок отображения после drag-and-drop. Инструмент восстановления вручную повреждённого контейнера.

## Decisions

- **ZIP, stored (no compression), not a custom binary or embedded-JSON-with-base64 format.** A plain ZIP with the `STORE` (uncompressed) method for every entry keeps the format inspectable/repairable with any standard ZIP tool (`unzip`, Archive Utility, 7-Zip), costs ~0 CPU to pack/unpack since MP3/JPEG are already compressed, and needs no custom parser beyond a ZIP library. `index.json` and cover images are tiny, so not compressing them costs nothing meaningful.
  - *Alternative considered*: SQLite file (like `.sqlite`-backed formats) with audio in a BLOB table. Rejected: loses "open with any archive tool" inspectability, adds a native dependency (better-sqlite3) with prebuilt-binary/asar-unpacking concerns across three OSes, and buys nothing over ZIP for this access pattern (whole-book files, not fine-grained queries).
  - **RU:** ZIP без сжатия (`STORE`), не кастомный бинарный формат и не JSON с base64-встроенным аудио. Обычный ZIP с методом `STORE` для всех записей остаётся читаемым любым архиватором, почти не требует CPU на упаковку/распаковку (MP3/JPEG уже сжаты). *Альтернатива*: SQLite-файл с аудио в BLOB — отклонено: теряется прозрачность формата, добавляется нативная зависимость с проблемами упаковки под три ОС, и не даёт выигрыша для такого паттерна доступа (целые файлы, а не точечные запросы).

- **Open = extract to a per-session working directory; edit the working directory; Save = re-zip it.** `openProjectFromFile` extracts the ZIP into `<tempDir>/audiopie-<sessionId>/`; all editing (add/remove tracks, chapter reorder, metadata edits, adding a book to a series) happens against real files in that directory, exactly like today's in-memory `ProjectData` but with `books/<bookId>/*.mp3` as real files instead of pointers. `saveProjectToFile` zips that directory to the target `.audiopie` path. This is the same lifecycle as `.docx`/`.pptx` (OOXML is literally a ZIP of an extracted-looking file tree) and keeps FFmpeg build logic untouched — it already only knows how to read real files.
  - **RU:** Открытие распаковывает ZIP в рабочую директорию сессии; редактирование идёт над реальными файлами в ней; сохранение — упаковывает директорию обратно в `.audiopie`. Тот же жизненный цикл, что у `.docx`/`.pptx`.

- **Copy-on-add for new tracks; copy-on-first-save only for legacy-JSON migration.** When the user adds an MP3 to a project that's already in container form (new project, or a legacy project already upgraded this session), the file is copied into the working directory's `books/<bookId>/` immediately — `tracks.addFromPaths` becomes copy-then-probe, not probe-then-record-path. But opening an *old* plain-JSON `.audiopie` does **not** eagerly copy anything (tracks keep pointing at their original external paths, exactly like today, so opening an old file stays instant even for a 20-track book) — the copy-into-container step for its *existing* tracks is deferred until that project's first Save, at which point every referenced external MP3 is copied into a freshly created working directory and the file is rewritten as a ZIP at the same path. This avoids doing a potentially multi-GB copy just because the user opened an old file to look at it, while still guaranteeing "copy happens immediately" for every track add that happens once we're already in container form (new tracks added to a legacy project *during* the session it's opened also follow copy-on-add into the pending working directory — only the pre-existing tracks from the JSON are deferred).
  - *Alternative considered*: copy everything only at Save time, always (including for brand-new projects). Rejected per explicit product decision — copy-on-add makes "what's in my project right now" match "what's on disk in the working directory" at every point, which is simpler to reason about and means Save is always just "zip what's already there", not "go copy N files then zip".
  - **RU:** Копирование при добавлении для новых треков; копирование при первом сохранении — только для миграции старых JSON. Открытие старого JSON не копирует ничего сразу (треки как раньше указывают на внешние пути); копирование существующих треков откладывается до первого Save этого проекта, когда создаётся рабочая директория и файл целиком переписывается как ZIP по тому же пути. Треки, добавленные *во время* этой же сессии к открытому старому проекту, уже копируются немедленно (copy-on-add), как и в проекте нового формата.

- **`index.json` is split: a tiny root manifest plus one self-contained `index.json` per book folder.** The root `index.json` holds only container-level facts — it never grows with chapter count:
  ```json
  {
    "version": 2,
    "type": "audiobook" | "series",
    "series": null,
    "bookOrder": ["book-a1b2c3d4"]
  }
  ```
  Each book's own metadata and tracks live in `books/<bookId>/index.json`, fully self-contained:
  ```json
  {
    "metadata": { "title": "...", "author": "...", "seriesIndex": null, "coverFile": "cover.jpg" },
    "tracks": [
      { "file": "1.mp3", "displayTitle": "Chapter 1", "durationMs": 612000 }
    ]
  }
  ```
  `type: 'series'` additionally has a `series: { title, author, narrator, description }` object at the root (see below — no series-level cover). `bookOrder` is the ordered list of book ids and is the single source of truth for display/series order; a `type: 'audiobook'` container always has exactly one entry in `bookOrder` and `series: null`. Chapters are *not* stored separately anywhere — they're derived from a book's own `tracks` array exactly as today's "1 track = 1 chapter, sequential start/end" rule.
  - *Why split instead of one monolithic `books: BookEntry[]` array*: for a large series (dozens of books), a monolithic array means editing *any* book's title rewrites the *entire* series manifest, and the manifest's size grows with total chapter count across every book. With a per-book `index.json`, editing one book only touches its own tiny file, the root manifest's size depends only on the number of books (not chapters), and — critically for the "series = books with more than one entry" model — a book folder becomes a fully self-describing unit: "extract this book as a standalone file" and "import a book from another file" both become "copy/read one folder", not "pluck an entry out of an array and reconstruct a wrapper". This also means an `audiobook` container's on-disk shape (`books/<id>/index.json` + its mp3s) is *identical* in structure to one member of a `series` container — switching `type` never touches `books/` at all (see the new "mutable type" decision below).
  - *Alternative considered*: one monolithic `books: BookEntry[]` array in the root `index.json` (the original draft of this design). Rejected after evaluating scaling to large (~30-book) series: acceptable in raw KB either way, but the monolithic shape has worse write-isolation (any edit anywhere rewrites everything) and worse composability (extract/import need to unwrap/rewrap an array entry instead of just moving a folder).
  - **RU:** `index.json` разделён: крошечный корневой манифест плюс собственный `index.json` в каждой папке книги. Корневой `index.json` хранит только факты уровня контейнера и не растёт с числом глав. Метаданные и треки каждой книги живут в `books/<bookId>/index.json`, полностью самодостаточно. `bookOrder` — единственный источник истины для порядка. `type: 'series'` дополнительно имеет `series: {...}` на корне (без обложки серии — см. ниже). *Почему разделение, а не монолитный массив*: изоляция записи (правка одной книги не трогает весь манифест), рост манифеста не зависит от числа глав, и папка книги становится самодостаточной единицей для extract/import.

- **No series-level cover.** A `series`'s shared metadata is `{ title, author, narrator, description }` — no cover image of its own. Only individual books have covers (`books/<bookId>/cover.<ext>`, referenced by that book's own `metadata.coverFile`). The series page's UI represents a series visually via its books' own covers (e.g. the first book's cover, or a stack/grid of them), not a dedicated series cover asset.
  - *Why*: removes the open question of "where does a series-level cover file live when there's no shared `covers/` directory" entirely, at the cost of not being able to set one deliberately-different "box set" cover — acceptable for v1.
  - **RU:** У серии нет собственной обложки. Общие метаданные серии — только `{ title, author, narrator, description }`. Обложки есть только у отдельных книг (`books/<bookId>/cover.<ext>`, через `metadata.coverFile` этой книги). UI страницы серии представляет её визуально через обложки книг, а не через отдельный файл обложки серии.

- **Book folder ids are assigned once at creation and never reused or renumbered.** `bookId` (the `books/<bookId>/` directory name) is an opaque stable identifier (e.g. `book-<8 random hex chars>`), decoupled from a book's position in `bookOrder` (which reflects display/series order and can be freely reordered) and from its `metadata.seriesIndex` (the user-facing manual series number). This mirrors the already-settled decision in the superseded change that drag-order and manual series numbering are independent.
  - **RU:** Идентификатор папки книги назначается один раз при создании и не переиспользуется/не перенумеровывается — не зависит ни от позиции в `bookOrder`, ни от `metadata.seriesIndex` (ручной номер серии).

- **Chapter MP3 filenames are stable storage keys, not a live mirror of display order.** A track's filename inside `books/<bookId>/` (`1.mp3`, `2.mp3`, ...) reflects the position it had *when it was added/copied*, and is never renamed afterward. That book's own `tracks` array (in its `books/<bookId>/index.json`) is the single source of truth for chapter order and is what drag-and-drop reordering rewrites; the filenames themselves become an unordered bag of content once reordering happens. This avoids renaming large media files on disk (slow, and risky mid-operation) purely for cosmetic tidiness inside the archive.
  - *Alternative considered*: re-number filenames to match order on every save so a manual unzip always shows `1.mp3, 2.mp3, ...` in chapter order. Rejected: for a 20+ chapter book this is 20+ file renames (or copies, since ZIP entries aren't renamed in place) on every save for zero functional benefit — the book's own `tracks` array is what every part of AudioPie actually reads.
  - **RU:** Имена файлов глав — стабильные ключи хранения, не отражение порядка отображения. Порядок определяется массивом `tracks` в собственном `index.json` книги; при перетаскивании физические файлы не переименовываются.

- **Project type is mutable after creation, from a Settings "danger zone" — not fixed forever at creation.** Because an `audiobook`'s and a `series`'s on-disk shape are structurally identical (both are just `bookOrder` + `books/<id>/index.json` folders — see above), switching `type` in Settings never has to move, copy, or restructure any book folder. `audiobook → series` is a free, non-destructive flip (adds an empty `series` metadata block; the existing single book keeps its place as `bookOrder[0]`). `series → audiobook` is destructive whenever more than one book exists — the system keeps only `bookOrder[0]` (the first book in current display order) and permanently deletes every other book folder — so it requires an explicit confirmation modal that names the deletion before proceeding.
  - *Why a confirmation modal rather than, e.g., auto-extracting the removed books first*: the analogous "remove one book from a series" flow (see `project-types` capability) offers "extract as standalone file" as a non-destructive alternative precisely because it's a *single*, deliberate removal. Collapsing a whole series down to one book is a different, rarer, explicitly-labeled "danger zone" action where a blunt warn-then-delete is clearer than bundling in a multi-file extract wizard; a user who wants to keep the other books should cancel and extract them individually first via the existing per-book flow.
  - **RU:** Тип проекта можно менять и после создания — из «опасной зоны» настроек, а не только один раз при создании. Поскольку `audiobook` и `series` структурно идентичны на диске, переключение типа никогда не требует перемещения папок книг. `audiobook → series` — безобидный флип. `series → audiobook` — деструктивно, если книг больше одной: остаётся только `bookOrder[0]`, остальные папки книг безвозвратно удаляются, поэтому требуется явное модальное подтверждение.

- **"Create new" requires picking a save location before the editor opens, for both `audiobook` and `series`.** `project.new(type, savePath)` writes a minimal container to `savePath` immediately (one empty book for `audiobook`; zero books for `series` until the user attaches/creates one) and opens a working directory for it, rather than editing an unsaved in-memory project and prompting for a path on first Save. This removes the old "guard against saving an empty project" problem at its root — there is no more untitled/unsaved state to guard against, since a path is chosen up front. It also means "Recent Projects" (separately proposed) can track a brand-new project immediately instead of only after its first meaningful save.
  - **RU:** «Создать новый» требует выбрать путь сохранения до открытия редактора, для обоих типов. Это убирает саму причину существования старой защиты «нельзя сохранить пустой проект» — неозаглавленного несохранённого состояния больше нет.

## Risks / Trade-offs

- [Risk] Migrating a legacy JSON project on its first Save copies every referenced external MP3 into the new working directory synchronously at that moment — for a long audiobook this could be several GB and take a noticeable amount of time, unlike today's near-instant JSON write → Mitigation: surface progress via a build-progress-style modal/IPC channel during that one-time migration; this cost is paid exactly once per legacy file (every Save after that is a normal repack of an already-populated working directory).
  - **RU:** [Риск] Миграция старого JSON при первом Save копирует все внешние MP3 синхронно — может занять заметное время для длинной книги → Смягчение: показать прогресс, эта стоимость платится один раз на файл.
- [Risk] Re-zipping a multi-GB working directory on every explicit Save is I/O-bound and could make "Save" feel slow for very long audiobooks (many hours / GB+ of MP3) → Mitigation: stream pack/unpack (never buffer a whole book in memory) using a ZIP library that supports streaming (e.g. `yazl`/`yauzl`); validate with a smoke test against a large synthetic audiobook; if main-process responsiveness during Save turns out to be a real problem, move packing to a Node worker thread as a follow-up (not required for v1 given `STORE` has near-zero CPU cost — this is disk I/O, not compute).
  - **RU:** [Риск] Упаковка многогигабайтной рабочей директории на каждое явное сохранение — I/O-операция, может ощущаться медленной для очень длинных книг → Смягчение: потоковая упаковка/распаковка, без буферизации всей книги в памяти; при необходимости — вынести упаковку в отдельный worker-поток.
- [Risk] Disk usage roughly doubles while a project is open (extracted working directory + the packaged `.audiopie` on disk) → Mitigation: this is the same trade-off every container-format editor (Office, image editors) already makes; clean up the working directory on project close and on app quit, and sweep orphaned `audiopie-*` temp directories left behind by a crash on next app start.
  - **RU:** [Риск] Использование диска примерно удваивается на время открытого проекта → Смягчение: тот же компромисс, что у любого редактора контейнерных форматов; очистка рабочей директории при закрытии/выходе и подчистка осиротевших временных папок при следующем запуске.
- [Trade-off] Chapter MP3 filenames don't reflect current display order after reordering (see Decisions) — someone manually inspecting the ZIP with an archive tool sees files in insertion order, not chapter order → accepted; `index.json` is the authoritative source, and AudioPie itself never needs filenames to be in display order.
  - **RU:** [Компромисс] Имена файлов глав не отражают текущий порядок отображения после перетаскивания — при ручном осмотре ZIP файлы идут в порядке добавления, не порядке глав → принято осознанно.
- [Risk] New-format containers are unreadable by any AudioPie version older than this change (opposite direction of the supported legacy-JSON migration) → Mitigation: this is a one-way, accepted breaking change (see Migration Plan); call it out clearly in the release notes/CHANGELOG.
  - **RU:** [Риск] Новые контейнеры нельзя открыть в версиях AudioPie старее этого change → Смягчение: осознанное одностороннее breaking-изменение, явно указывается в CHANGELOG.
- [Risk] Switching a project's type from `series` to `audiobook` via the Settings danger zone permanently deletes every book folder except `bookOrder[0]` — a user could lose books they meant to keep if they click through the warning too quickly → Mitigation: the confirmation modal explicitly names how many books will be deleted before proceeding; deletion only happens on the next Save (not the instant the toggle is flipped in the UI), matching every other destructive edit in this app's working-directory model, so a user can still back out by not saving.
  - **RU:** [Риск] Переключение типа с `series` на `audiobook` через «опасную зону» настроек безвозвратно удаляет все папки книг кроме `bookOrder[0]` — пользователь может случайно потерять книги, слишком быстро проскочив предупреждение → Смягчение: модалка явно называет число книг, которые будут удалены; удаление применяется только при следующем Save, как и любая другая деструктивная правка в модели рабочей директории — можно откатиться, не сохраняя.

## Migration Plan

- **Forward (old → new), automatic, per-file, on first Save**: covered in Decisions above — no explicit user-facing "migrate my library" step; a user's existing `.audiopie` files upgrade themselves the next time each is saved, one at a time, as a natural side effect of normal use.
- **Versioning**: bump `index.json`'s `version` to `2` (from today's `1`) as the container-format marker; `project.ts`'s open logic sniffs the file's first bytes (`PK\x03\x04` ZIP local-file-header signature vs. a JSON-looking `{`) to decide legacy-JSON vs. container path, rather than trusting the file extension alone.
- **App version**: ship behind a semver-major-ish bump (per this project's own release conventions) given the on-disk format change is user-visible and one-directional; CHANGELOG explicitly notes "projects saved with this version can't be opened by older AudioPie."
- **Rollback**: there is no automated downgrade path for a container-format file back to plain JSON. A user who needs to go back to an older AudioPie version keeps using their not-yet-resaved legacy files (unaffected — opening never rewrites without an explicit Save) and simply avoids saving with the new version until ready to commit to the upgrade. An explicit "export as legacy JSON" escape hatch is a non-goal for v1 (see Non-Goals).
- **`project-types-and-series` change**: mark its `proposal.md` with a superseded notice pointing at this change; leave its artifacts in place (not archived as completed, since it was never actually implemented) for historical reference. Its UI-level decisions (unified series page, manual `seriesIndex` numbering decoupled from list order, "Add book" FAB menu, "Part of series" callout) are carried forward into this change's `project-types` capability rather than re-derived from scratch.

**RU:** Миграция вперёд (старый → новый) — автоматическая, по файлу, при первом Save, без отдельного шага «мигрировать библиотеку». Версия `index.json` повышается до `2`; определение формата — по сигнатуре байт (ZIP vs JSON), не по расширению. Версия приложения — с учётом breaking-изменения формата, с явной пометкой в CHANGELOG. Откат назад не поддерживается автоматически; старые несохранённые файлы остаются читаемыми в старых версиях. `project-types-and-series` помечается как заменённый (superseded), его UI-решения переносятся в capability `project-types` этого change.

## Open Questions

- Should the one-time legacy-migration Save show an explicit confirmation dialog ("this will convert N files into the new project format, continue?") before copying, or proceed silently with just a progress indicator? Leaning toward a lightweight one-time confirmation since it's copying potentially several GB and changing the file's on-disk semantics — but not blocking creation of this change on resolving it now.
- Final ZIP library choice (`yazl`/`yauzl` vs. `adm-zip` vs. `archiver`/`node-stream-zip`) is left to the implementation task that spikes streaming pack/unpack against a large synthetic audiobook; the constraint that matters (streaming, no native/prebuilt-binary dependency, cross-platform) is fixed here, the specific package is not.
- Whether ZIP packing on Save should be offloaded to a Node worker thread is deferred pending a real-world timing measurement (see Risks) rather than decided speculatively now.

**RU:** Открытые вопросы: показывать ли подтверждение перед миграцией старого файла при первом Save; финальный выбор ZIP-библиотеки — по итогам спайка на потоковую упаковку/распаковку; вынос упаковки в worker-поток — по итогам реальных замеров времени.

## Implementation Note: ZIP library choice (resolves task 1.1)

- **Chosen: `yazl` (pack) + `yauzl` (unpack).** Both are pure-JS, zero native dependencies, and stream entries instead of buffering a whole archive in memory — `yazl.ZipFile#addFile` streams a source file straight into the output write stream, and `yauzl.open` + per-entry `openReadStream` streams a decompressed entry straight to a destination write stream. This satisfies the cross-platform (macOS/Windows/Linux) and no-native-binary constraints without any asar-unpacking concerns (unlike a native module).
- `zipDirectory`/`unzipToDirectory` (in `electron/main/projectFile.ts`) walk the directory tree and add/extract one entry at a time using `compress: false` (yazl) — i.e. the ZIP `STORE` method — matching the Decisions section above.
- Rejected alternatives: `adm-zip` buffers entire entries (and often the whole archive) in memory, which conflicts with the "streaming, bounded memory" goal for multi-GB audiobooks. `archiver`/`node-stream-zip` are viable streaming alternatives but `yazl`/`yauzl` are the smaller, more widely-used (used by VS Code itself) pairing for this exact pack/unpack use case.

**RU:** **Выбор:** `yazl` (упаковка) + `yauzl` (распаковка) — обе библиотеки чистые JS, без нативных зависимостей, потоковые (не буферизуют архив целиком в памяти), что удовлетворяет требованиям кроссплатформенности и отсутствия нативных бинарников. Отклонённые альтернативы: `adm-zip` буферизует записи/архив целиком в памяти; `archiver`/`node-stream-zip` — жизнеспособные потоковые альтернативы, но `yazl`/`yauzl` компактнее и шире используются (в частности, в VS Code) для этого конкретного сценария.
